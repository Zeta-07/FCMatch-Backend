# Decisiones técnicas — Fase 0

## DT-015 — Etapa 6: número público y compatibilidad explícita

El propietario aprueba corregir Etapa 6, sin aprobarla definitivamente ni avanzar a Etapa 7. Se conserva `users.id` UUID interno y `public_id` UUID anterior. Se añade `public_number` integer, único e inmutable, rango 10000000–99999999, secuencia NO CYCLE: 90 millones de asignaciones, huecos válidos y sin reciclado tras eliminación o rollback de una transacción. No se emplea como credencial, JWT subject, permiso ni relación interna. El acceso público sigue limitado y no expone correo, ID interno ni sesiones; la numeración es enumerable, no secreta. La API asigna automáticamente mediante el default de PostgreSQL y rechaza asignación masiva en registro/edición.

Migraciones nuevas expand/finalize; nunca se reescriben las anteriores ni se deshabilitan sus triggers. Inventario local previo: una cuenta dev, cero test. Expand incorpora columna nullable, default, índice único y trigger; finalize completa los nulos y valida NOT NULL/rango. Para más de 10000 pendientes se detiene antes del backfill masivo: `npm run db:migrate -- --public-number-expand`, `node --env-file=.env --import tsx scripts/backfill-public-numbers.ts` (500 filas por transacción, reanudable), verificar cero nulos y `npm run db:migrate`. Se admite el código anterior durante expand. Ejecutar con respaldo verificado y permisos de migración, en ventana controlada: DDL con lock_timeout 5 s y singleTransaction, sin promesa de cero bloqueo. Rollback operativo: aplicación anterior conservando esquema, números y secuencia; Down deliberadamente rechaza destruir asignaciones. No reiniciar secuencia; restauraciones deben preservar su avance para no reciclar números.

La respuesta predeterminada application/json conserva exactamente las propiedades anteriores. Accept `application/vnd.fcmatch.identity.v2+json` añade publicNumber como string de ocho dígitos en perfil propio/público, edición, confirmación de correo y búsqueda; respuesta con Vary: Accept. Ambas representaciones mantienen el UUID público anterior. Los clientes nuevos solo presentan/copian publicNumber y crean enlaces numéricos; enlaces UUID antiguos siguen resolviendo. Cursores HMAC, ordenación y UUID de desempate no cambian. Búsqueda por número mediante filtro exacto publicNumber, excluyente con search/cursor: un username de ocho dígitos no se interpreta como ID. Modelos regenerados para los tres clientes. Referencias: Frontend DT-013 y AdminWeb DT-012.

Se conservan las excepciones aprobadas Angular 22.2.4/TypeScript 6.0.3; npm outdated detecta Angular 22.2.6 y TS 7.0.2, sin ampliar esta corrección a una actualización de stack. `.local/` se excluye del lint/formato por contener utilidades locales no versionadas del entorno, no fuentes de producción.

## DT-014 — Etapa 5 y almacenamiento S3 local real

El propietario aprueba Etapa 4 y autoriza Etapa 5 sin interfaces. Posteriormente sustituye R2 de desarrollo por S3 local para evitar registrar tarjeta. Se selecciona **SeaweedFS 4.53**, Apache-2.0, mantenido y con binarios Windows/Linux: verificación de release y SHA-256 oficial, sin Docker necesario. MinIO se descarta por repositorio archivado; Garage/RustFS activos, pero SeaweedFS ofrece mejor ajuste nativo y operativo en este entorno. R2 sigue previsto para producción y su integración real queda explícitamente pendiente. Adaptador `disabled|s3-local|r2`, sin fallback; local solo HTTP en 127.0.0.1 y nunca producción. Credenciales aleatorias ignoradas, buckets/identidades dev y test separados, sin anónimo/Admin para el backend, listeners loopback y filer HTTP deshabilitado; volumen requiere JWT interno. Puertos internos gRPC son parte del entorno local de confianza, no aptos para exposición pública. Scripts de descarga/arranque y CI verifican hashes fijados.

Fotos: máximo 5 MiB, 16 777 216 píxeles/8192 por lado, una imagen estática, firma/MIME y decodificación con sharp 0.35.5, recodificación sin EXIF/GPS/XMP. Multipart busboy 1.6.0 y concurrencia limitada; SDK/presigner estables 3.1167.0. Diario técnico `avatar_objects` con reservas/activos/retirados recupera fallos DB/S3 sin transacción distribuida, sin borrar claves activas ante commit ambiguo. Migraciones nuevas, nunca reescritura de las aplicadas. Una corrección aditiva alinea el diario con las claves de 32 hex ya exigidas por users; también reconoce reservas UUID previas para limpieza. No tablas de competición ni jobs de otras fases.

La cookie CSRF amplía Path a `/api/v1`, conservando refresh en `/api/v1/auth`: con el Path anterior el navegador no enviaría la prueba HttpOnly a `/users`. Payload firmado v2 permite migrar/limpiar el Path antiguo, conserva binding de familia y reutilización entre pestañas. Lecturas protegidas verifican Bearer/Origin/sesión sin exigir prueba de mutación; escrituras revalidan usuario→raíz dentro de su transacción. Perfil público se construye por lista explícita sin correo/hash/ID interno. Cursor HMAC ligado al prefijo, orden por lower(username) COLLATE C y publicId. Cambio de correo mantiene dirección anterior hasta consumo del token del titular, contraseña actual/abuso compartido, destino distinto revoca anterior y unicidad final genérica. Revoca tokens sensibles pendientes al confirmar, sin revocar sesiones ni autenticar automáticamente. Ver informe de Etapa 5.

## DT-013 — Etapa 4 autorizada: sesiones y contraseña sin perfiles/UI

El propietario aprueba Etapa 3 y autoriza Etapa 4, con commits/push tras checks y actualización de PR #5; no fusiones, force push o Etapa 5. JWT HS256/jose 6.2.17, issuer API origin, audiencias/contextos separados y clave aleatoria independiente obligatoria; access ≤15 min y vencimiento absoluto. Refresh 32 bytes, hash e historial sobre tablas aplicadas, vida absoluta 30 días, rotación estricta sin gracia. CSRF se liga a raíz en payload firmado, login renueva contexto y bootstrap/refresh no invalidan innecesariamente pestañas. Autorización consulta BD, no solo JWT. Orden usuario→raíz→generación y replay revocado durablemente antes del 401; login/cambio revalidan hash bajo lock tras Argon. Login/clave actual comparten bloqueo de identidad; Argon comparte semáforo máximo dos. Recuperación 30 min con política SMTP genérica existente; reset/cambio revocan todas las sesiones y tokens sensibles pendientes, sin login automático. No tablas/migraciones nuevas. Pérdida de microsegundos al reinsertar expires_at corregida con INSERT SELECT en PostgreSQL, sin truncar BD o relajar integridad. Evidencia/límites: `docs/fase-1-etapa-4-verificacion.md`. Modelos no cambian de forma; clientes sin auth/interfaz nueva, Web Locks pendiente de su etapa.

## DT-012 — Registro y verificación ejecutables, sin login

Etapa 3 implementa únicamente registro, verificación y reenvío, más bootstrap/protección CSRF exigidos por el contrato existente. Argon2 0.45.2 precompilado, instalado sin scripts: Argon2id 64 MiB/t3/p1/salida32, calibración Windows hash+verificación 281–303 ms, máximo dos hashes en paralelo sin cola. Límites persistentes y HMAC de IP/identidad usan las tablas aplicadas, sin nueva migración; usuario se bloquea antes de consumir/invalidar tokens hermanos. SMTP fuera de transacción, presupuesto de espera 5 s, aceptación genérica y piso HTTP de 6 s para reducir enumeración por latencia; un timeout conserva token. No hay garantía de tiempo constante bajo sobrecarga. Cookies CSRF independientes host-only y firmadas de 1 h no son sesiones; secretos independientes obligatorios, solo configuración local/CI, sin defaults. Configuración de producción falla si HTTP o hostnames distintos (criterio conservador de compatibilidad SameSite). El mensaje apunta a una ruta web futura con token en fragmento, sin crear UI ni acción GET. Las 15 operaciones restantes siguen planned. AWS se actualizó al parche estable 3.1167.0 en commit separado con check completo; Angular 22.2.4/TS 6.0.3 conservan excepciones existentes. Detalle y límites en `docs/fase-1-etapa-3-verificacion.md`. Publicación de Etapa 3 expresamente autorizada si checks satisfactorios; no integración ni Etapa 4.

## DT-010 — Etapa 1 aprobada y persistencia exclusiva de Etapa 2

El 11/11/2026 el propietario aprueba los resultados de Etapa 1 y la excepción temporal Angular 22.2.4; queda resuelta la solicitud de aprobación que DT-009 conserva como antecedente. No se fuerza 22.2.5 ni se relajan peers. Se conservan contrato, políticas y pruebas. Se autoriza exclusivamente crear `users`, `sessions`, `action_tokens` y `login_attempts`, con una migración nueva, restricciones, índices y pruebas PostgreSQL reales; no endpoints, servicios de autenticación, UI, R2 ni nuevas funciones. No sustituyen validación de credenciales ni implementan el flujo de autenticación. Referencias de la excepción: DT-010 de Frontend, DT-009 de AdminWeb. ## DT-003 — Versiones estables compatibles

Node 26.13.0 LTS, npm 12.2.1, Express 5 y PostgreSQL 18.6, comprobados en fuentes oficiales. TypeScript 7.0.2 es la última estable publicada, pero Angular compiler-cli 22 exige `>=6.0 <6.1` y typescript-eslint exige `<6.1`. Se fija la última estable compatible, TypeScript 6.0.3, en los cuatro paquetes. No se fuerza la resolución ni se oculta esta incompatibilidad.

`openapi-typescript` 7.13.0 exige TypeScript 5; se elige `@hey-api/openapi-ts` 0.99.0 compatible. Se validó generación y compilación.

## DT-004 — Dependencias transitivas

La auditoría inicial de las últimas versiones detectó avisos en minimatch, glob y js-yaml. Se fijan overrides a minimatch 11.0.4, glob 14.0.3 y js-yaml 5.5.0, todos estables corregidos. Tipos, generador, lint, migraciones y pruebas verifican la combinación; `npm audit` queda sin vulnerabilidades. Los lockfiles fijan la resolución.

## DT-005 — Infraestructura local y servicios externos

El usuario autorizó PostgreSQL local y correo exclusivamente local, dejando R2 pendiente de credenciales. Bases `fcmatch` y `fcmatch_test` separadas, rol de aplicación sin privilegios de superusuario, contraseñas aleatorias excluidas de Git, UTC y escucha en loopback. El adaptador R2 no simula conectividad si falta configuración.

## DT-006 — Calidad y separación de repositorios

Pruebas HTTP con Node Test Runner y Supertest, integración con PostgreSQL real y recepción SMTP técnica. CI propio con PostgreSQL efímero. Los clientes reciben los tipos generados por copia controlada; ningún cliente importa archivos fuente de este repositorio por rutas relativas. API y UI siguen siendo productos independientes.
